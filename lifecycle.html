Make the next decision easier by giving it clear evidence from the previous one.

Why faster coding isn't enough

Suppose a change takes one day to code and four days to clarify, review, and release. Cutting coding to an hour still leaves most of the wait. Generating more changes can even make the review queue longer. Traditional controls were built for good reasons: agreement on scope, evidence of quality, and accountability for releases. Keep those objectives; change when and how you get the evidence.

The core shift: Don't ask for an implementation and then try to infer what it does. Agree on the outcome first, give the agent the approved context and boundaries, and verify the result against evidence you can inspect. Use AI throughout the lifecycle, not only to type code. People still approve scope, trade-offs, risk, and release decisions.

Think of a shared kitchen. The order says what the customer wants, the recipe specifies how it should turn out, the cook makes it, a check confirms it matches the order, and service feedback improves the next recipe. Even if one person does all the work, these are different decisions. The same applies to a solo developer and six SDLC stages.

Follow the evidence: Approved intent.md → spec.md → implementation plan.md and diff → passing tests and findings → PR and release record → incident or feedback → new intent. If verification fails, fix the code or revisit Design; don't move forward on an unexplained failure. For a small fix these could be sections in one PR, not six documents.

Plays are practices, not phases

A stage answers a lifecycle question. A play is a repeatable way to improve how you answer it, with a starting condition, steps, a control, and a measure. You can adopt a Test play before redesigning how you capture requirements.

A practical adoption map

The six numbered lessons below follow Anthropic's playbook. For a first rollout, use this simplified sequence by dependency rather than trying everything at once:

  1. Start where the queue is: Capture intent in Git, document repo conventions in CLAUDE.md, teach a repeatable checklist through a skill, or give Claude a fast test command. Start with one change.
  2. Build on the basics: Turn an accepted intent into a design. Start a scoped Plan Mode session from the spec and rules. With shared conventions and reliable checks, try worktrees, subagents, or continuous evals of agent configuration.
  3. Strengthen the release path: Review PRs against agreed rules and test evidence. Practice deterministic hooks and require server-side checks. Rehearse rollback and verify permissions before considering agent-assisted CI/CD.
  4. Close the loop: After you have a reviewed way to record intent and handle releases, let a trusted alert produce a draft follow-up for triage. Start with read-only diagnosis; keep human approval for changes.

In this course you approve and hand off artifacts manually. In a mature system a trusted event can trigger the next check, but an event is not permission to deploy.

01 · Intent

Plan: agree on the problem

Why separate it: Drafting requirements is faster than discovering you solved the wrong problem. Capture the user's wording while it's fresh, and review it before judging solutions.

Play: Start from an idea, ticket, or incident. Ask Claude to identify the user, pain, outcome, exclusions, and open questions. Have the owner correct it and version the result as intent.md. Track time from request to accepted intent and how often implementations reopen scope.

Greenfield: A support operator wants to queue a synthetic notification once per request. Real email and persistent queues are out.

Brownfield: Finance wants one CSV for a small batch; existing clients must still get the same single-invoice CSV.

Try it: Make “faster exports” testable

Expected: “An operator can submit a batch of up to 10 known unique invoice IDs and receive one CSV in request order. Existing single exports are unchanged.” Leave latency targets open until you have a baseline.

Handoff: Design reads the accepted intent, not the original chat. Greenfield lab · Brownfield lab

02 · Spec

Design: make behavior and trade-offs explicit

Why separate it: You can compare contracts and failure behavior without paying to undo an implementation. The spec gives testers, developers, and the agent the same target.

Play: Supply the intent and relevant standards. Ask Claude for two alternatives and observable acceptance cases. Have a person choose the design and record trade-offs, risks, and non-goals in spec.md. Watch for requirements changed during review and design-driven rework.

Greenfield: Start with in-memory deduplication and a fake outbox rather than setting up a real queue. Document that restart resets state.

Brownfield: Add a flagged function instead of replacing the CSV interface. Reject a bad batch before returning any export.

Try it: Decide what a duplicate means

Expected: A repeated notification request ID is a no-op; duplicate invoice IDs in one batch are an input error. Similar words can require different rules.

Handoff: Build reads the agreed behavior and constraints. Greenfield lab · Brownfield lab

03 · Plan and diff

Build: approve a small implementation and make it real

Why separate it: The Plan stage defines why; Claude Code's Plan Mode during Build works out how and what to verify before editing. A small diff and explicit change boundaries reduce review effort.

Plays: Start in Plan Mode with spec.md and CLAUDE.md. Ask for file-level changes, risks, and a test command; approve a small slice and record plan.md. Use skills for repeatable procedures, hooks for deterministic checks, and subagents or separate worktrees only for bounded independent work. Measure rework and time to first verified diff, not generated lines.

Greenfield: Implement one submit-to-fake-outbox path first, then add duplicate and invalid input handling.

Brownfield: Run baseline tests, trace the existing CSV formatting, then add bulk behavior in a short-lived worktree without changing the existing interface.

Try it: Spot a plan that is too big

Expected: “Replace the entire export module and add async jobs” exceeds the approved change. Ask for the smallest additive path and a verifiable compatibility check.

Handoff: Test receives the diff, changed assumptions, and commands. Greenfield lab · Brownfield lab

04 · Evidence

Test: make feedback quick and independent

Why separate it: The author can misunderstand the requirement and write tests that confirm the same misunderstanding. An independent check and a repeatable command protect against that.

Plays: Give Claude a short feedback command during implementation, then check the diff against the approved spec with fresh context. Keep two kinds of checks distinct: product tests verify behavior; continuous evals check whether an agent with changed prompts, rules, or models still handles representative tasks well. Track feedback time, false alarms, and escaped defects.

Greenfield: Check accepted requests, duplicate IDs, and blank messages; inspect the outbox rather than trusting a successful return alone.

Brownfield: Re-run legacy tests and independently inspect request order, missing IDs, the batch limit, and flag-off behavior.

Try it: Interpret a failing duplicate check

Expected: If the accepted spec says one message per ID, fix the code, rerun checks, and leave the approval criterion intact. If the spec is wrong, take the question back to its owner.

Handoff: Deploy receives test evidence tied to the candidate revision and known risks. Greenfield lab · Brownfield lab

05 · Release

Deploy: ship with a decision, not just a green check

Why separate it: Tests describe the candidate. A release verifies what reached the target and whether it's safe to keep there.

Plays: Add agent-assisted PR review to flag missing evidence and decisions. Enforce required checks and human approvals through trusted hooks where applicable and GitHub rules at the repository boundary. Before agent-assisted CI/CD, restrict permissions, separate deployment from untrusted PR execution, and practice rollback. Measure review wait, failed releases, and rollback time.

Greenfield: Run a local smoke check from a clean checkout and keep the previous candidate revision available.

Brownfield: Ship with bulk export off; test legacy behavior, enable the flag in simulated staging, smoke test, then turn the flag back off to rehearse rollback.

Try it: What do you do when a smoke check fails?

Expected: Stop rollout, use the approved rollback path, verify the restored behavior, and record the revision and evidence. Don't let a review bot grant its own release approval.

Handoff: Maintain reads the candidate revision, smoke evidence, and rollback notes. Greenfield lab · Brownfield lab

06 · Feedback

Maintain: turn observations into the next intent

Why separate it: Production exposes cases fixtures didn't. A useful incident note preserves observations instead of jumping from a noisy alert to an unreviewed fix.

Play: Start from a trusted alert or support report, supply sanitized evidence, ask Claude to separate facts and hypotheses, and assign an owner. Review any mitigation and capture the follow-up as a new intent.md. Track detection-to-triage time and repeat incidents.

Greenfield: A simulated delivery failure shows a missing retry signal. Record evidence and plan retry visibility, not an automatic resend.

Brownfield: A simulated latency breach calls for flag rollback and a follow-up to profile the end-to-end export path.

Try it: Rewrite “make export faster” after an alert

Expected: “Find why the synthetic bulk export exceeded 250 ms in two consecutive windows. Record the measured contributor and preserve existing CSV behavior.” Treat the threshold as a lab assumption, not a production recommendation.

Handoff: The approved follow-up re-enters Plan with links to release and incident evidence. Greenfield lab · Brownfield lab
