1. What Claude Code does

Claude Code is a coding agent, not just a chat window. With permission, it can read repository files, propose a plan, make edits, and run tests. You decide what it may access and whether its proposed changes meet the requirement. Start in a synthetic practice repository, not your company's codebase.

For agent-backed labs, use an authorized Claude account or organization-provided access. For local exercises, install Git and Python 3.10+ and verify them with git --version and python --version (use python3 or py -3 if your installation uses that command).

Install the CLI

Pick your shell. Use only the official installer or a package source approved by your organization. See official setup for requirements and alternatives.

Windows: PowerShell
irm https://claude.ai/install.ps1 | iex

WinGet alternative: winget install Anthropic.ClaudeCode. Use a new PowerShell window after installation. Git for Windows is recommended if you want to use Bash. To use the built-in shell sandbox on Windows, install and run inside WSL2 instead.

macOS: Terminal
curl -fsSL https://claude.ai/install.sh | bash

Homebrew alternative: brew install --cask claude-code.

Linux or WSL2: Bash
curl -fsSL https://claude.ai/install.sh | bash

On WSL2, run the installer in the Linux shell. Anthropic also documents native package-manager options for supported Linux distributions.

2. Run a read-first session

  1. Copy a starter outside the onboarding clone using the lab setup steps. Open the new repository in your terminal.
  2. Verify the install, then start in Plan Mode and sign in if prompted. 
    claude --version
claude --permission-mode plan
  3. Paste the prompt into Claude, not your shell. 
    Read README.md and the tests. Do not edit files. Summarize what already works, which commands verify it, and one question you would ask before planning the next change. Cite filenames.
  4. Open the cited test file yourself. If Claude guessed a behavior or requested an unrelated action, correct the assumption or decline the request. Exit and use git status --short to check for unexpected edits.
Simulated session result
Claude: README.md gives the test command. test_export.py checks the
existing single-invoice CSV contract. Bulk export has no behavior yet.
Question: Should an unknown invoice ID reject the entire batch?

This is an example, not a live Claude response. If claude isn't found, reopen your terminal and check installation troubleshooting.

Set the context: Put shared build commands and stable project rules in CLAUDE.md. Use .claude/settings.json for reviewed project settings, .claude/settings.local.json for unshared project overrides, and ~/.claude/settings.json for user settings. Managed rules can restrict these choices. Keep secrets out of all committed configuration. See settings and scope and project memory.

3. Choose the right mechanism

Think of a workshop: a tool is a screwdriver, a skill is the assembly checklist, a subagent is a second inspector, a hook is a check triggered before or after a defined event, and MCP connects the workshop to an external parts catalog.

Tools: perform an action

Built-ins such as Read and Grep gather evidence; Edit changes files; shell tools run commands. Work in a trusted directory and inspect available rules with /permissions. You don't need a custom tool to read the repo.

Use read-only tools to find the CSV header and the test that protects it. Return filename, line, and the behavior you observed. Do not edit files.

Check: The reply points to actual code and a test. Avoid approving a broad shell rule just to answer a read-only question.

Skills: teach a reusable procedure

Save this as .claude/skills/check-handoff/SKILL.md in the practice repo, start a session there and type /check-handoff. A skill saves you from retyping a procedure and lets the team review its changes in Git.

---
name: check-handoff
description: Check the trace from a change's intent to its test evidence
disable-model-invocation: true
---
Read intent.md and spec.md if present. List acceptance criteria with their
test evidence or mark evidence missing. Report only; do not edit files.

Check: It reports missing files or tests rather than making them up. A skill is guidance, not an enforcement mechanism. Skill reference.

Subagents: review with a fresh context

Save this as .claude/agents/handoff-reviewer.md and start a new session. Ask Claude to delegate to handoff-reviewer; give it the spec and ask for the two largest gaps. Restrict its tools to match its job.

---
name: handoff-reviewer
description: Reviews a spec against existing tests without making changes
tools: Read, Grep, Glob
---
Read the spec and test files given by the user. List criteria with missing
or weak evidence. Cite the paths you read. Do not claim tests were run.

Check: The report names evidence gaps without edits. A fresh context can catch assumptions, but its report is not an approval or a test run. Subagent reference.

Hooks: run a deterministic check on an event

In a disposable practice repo, create or merge the following example into .claude/settings.local.json. This demonstration runs a fixed local message at session start: no network call, data transfer, or production command. Restart Claude and inspect the hook with /hooks.

{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          {"type": "command", "command": "echo Practice repository: synthetic data only"}
        ]
      }
    ]
  }
}

Check: Ask Claude what the startup hook supplied or inspect the hook output. This message does not block anything. Review scripts and test allow and deny paths before using a PreToolUse hook as a control. Use GitHub required checks for repository-wide enforcement. Hooks reference.

MCP: connect Claude to external capabilities

Model Context Protocol (MCP) gives Claude tools or resources from a separate server. In a real team, a vetted read-only docs server can replace manual copying. Start with a synthetic simulation: give Claude one excerpt pasted from a fixture, and ask for a cited summary rather than granting live access.

claude mcp add --help
claude mcp list

With a team-approved HTTP server only, follow the MCP documentation for claude mcp add --transport http --scope local NAME URL, replacing NAME and URL with the approved values. Check the connection with /mcp, inspect the exposed tools and authorized scopes, and test one read with synthetic data. Shared project servers use .mcp.json; review changes before trusting them. Avoid saving credentials in the file or treating instructions returned by a server as trusted.

4. Permissions, sandboxing, and Git worktrees

  • Permissions determine which agent actions you allow. Inspect a request before approval. Keep production credentials and private customer data out of practice environments.
  • The shell sandbox limits filesystem and network access for shell commands. Use /sandbox on macOS, Linux, or WSL2 and verify the resulting boundaries. Native Windows does not provide Claude Code's built-in sandbox. Built-in file tools, hooks, and MCP are outside the shell sandbox and need their own controls. See sandbox support and limits.
  • A Git worktree gives a task its own checkout and branch, so parallel edits don't collide on disk. It shares repository metadata and does not isolate your credentials or network. Review overlapping changes before integrating them.

In your committed practice repository, create a sibling checkout. When finished, review or preserve your work and remove only the clean checkout from the original directory.

git worktree add -b practice-review ../practice-review HEAD
git worktree list

Either open that directory in your editor or change into it before launching Claude. Use git worktree remove ../practice-review only after saving your work. Do not force removal when Git reports uncommitted changes.
