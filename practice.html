Start in the browser or run the lab locally

Browser: Choose Greenfield or Brownfield. At each step, make the decision yourself, then reveal a simulated result. The browser does not run commands or contact Claude.

Local: Install Git and Python 3.10+ and use Claude Code setup if you want to practice with the agent. You can perform the steps by hand without Claude.

  1. Clone the GitHub repository (or download its ZIP). Copy the three files from your selected labs/CASE/starter folder into a new folder outside that checkout. Do not copy the repository's agent settings. Use a new folder for each lab.
  2. Open your terminal in that folder, initialize Git, and run the baseline. Use python3 or py -3 in place of python throughout if needed. 
    git init
python -B -m unittest -v
git add -- README.md *.py
git commit -m "Save lab baseline"
    If Git asks for identity, configure it for the practice repo using your own name and preferred GitHub email. If a Python import fails, check that all three starter files sit beside each other and rerun from that folder.
  3. Use the artifact templates when recording decisions. Paste each prompt into Claude, not the terminal. Review artifacts before allowing edits or handing them to the next stage.

Greenfield: notification outbox

A support operator wants to queue a synthetic notification once per request. You own the contract, but you don't need a queue, credentials, or an email provider. Starter: README · fake outbox · baseline test.

1 · Plan2 · Design3 · Build4 · Test5 · Deploy6 · Maintain
01 · Intent

Choose the smallest useful outcome

  1. Read the brief above. Decide which operator action must work and what you won't build.
  2. Ask Claude to draft intent.md. Correct the draft before moving on.
Interview me about a local duplicate-safe notification outbox. Draft intent.md
with the user need, observable success, constraints, and questions. No code,
network, real recipients, or persistent queue. Do not assume retry behavior.
Reveal simulated result

Accepted intent: Given two valid submissions with the same request ID, the operator can verify only one outbox entry. Real delivery and restart recovery are out of scope.

Proceed when: You can explain who needs it and how to observe success. Next: Design

02 · Spec

Agree on a contract before writing code

  1. Read the fake outbox and compare in-memory deduplication with durable storage.
  2. Choose an interface and document what happens for new, repeated, and blank input in spec.md.
Read intent.md and outbox.py. Compare an in-memory set with a durable store.
Propose acceptance cases for a new ID, a repeat with changed text, and blank ID
or message. Name the restart limitation. Draft spec.md; do not implement.
Reveal simulated result

Spec: submit(request_id, message) returns queued or duplicate; valid repeats retain the first message; whitespace-only inputs raise ValueError. The in-memory state resets on restart.

Proceed when: Each case has an observable result. Next: Build

03 · Plan and diff

Implement one submit-to-outbox slice

  1. Start Claude with claude --permission-mode plan. Request a minimal plan and review its proposed file list.
  2. Save the agreed plan.md. Exit Plan Mode through the approval interface when ready, then ask for the approved slice. Inspect git status --short and the new files.
Plan from spec.md. Add NotificationService in notifications.py and tests
alongside the starter. Use only FakeOutbox and the standard library. Explain
how to verify the smallest useful slice before you change anything.
Reveal simulated result

Claude proposes notifications.py and test_notifications.py; the original fake outbox stays unchanged. If it proposes a real queue or network, shorten the plan before approving.

Proceed when: You can trace the diff to the spec. Next: Test

04 · Evidence

Verify behavior, not just the return string

  1. Run the full suite. Check that the duplicate test asserts the outbox still contains the original entry.
  2. In a fresh session or with the review subagent, compare the tests to the spec. Repair any real gap and rerun.
python -B -m unittest -v
Review the tests against spec.md. Did we assert that a repeat leaves exactly
one original outbox entry and that invalid input never writes? List gaps
without editing tests or claiming a run you did not observe.
Reveal simulated result and worked solution

Baseline: 1 test. Worked solution: 4 tests, including the baseline. Overlay notifications.py and test_notifications.py on a fresh starter copy and rerun. If your suite differs, compare assertions rather than test count alone.

Proceed when: You have test output and can explain why it proves the requirement. Next: Deploy

05 · Release

Rehearse publishing safely

  1. Review the change and commit it on your practice branch. Open a PR only if you have a separate practice remote; a local release record is fine.
  2. Run this smoke test from a clean checkout of the candidate. Record the candidate revision, observed result, approver, and rollback plan.
python -B -m unittest -v test_notifications.NotificationTests.test_new_request_is_queued
git rev-parse --short HEAD
Reveal simulated result

One smoke test passes. The reviewed revision and the tested revision match. If it fails, do not release; return to the last verified revision in staging and rerun its baseline check. This lab does not deploy anything.

Proceed when: A second developer can reproduce the decision from release.md. Next: Maintain

06 · Feedback

Use an alert to write the next intent

  1. Read the simulated event. Separate facts from theories before deciding on a follow-up.
  2. Record the observed failure in incident.md and draft a new intent. Do not implement retries during triage.
SIMULATED 09:14 notice-7 adapter_timeout
SIMULATED 09:15 notice-7 status_unknown
Use the two synthetic events to draft incident.md. Separate facts from
unknowns, propose one measurable follow-up for delivery-state visibility,
and explain why resending now could duplicate a notification.
Reveal simulated result

Delivery is unconfirmed, not proven lost. Follow-up intent: an operator can distinguish pending, confirmed, and unknown delivery in a synthetic timeout test. The next cycle starts with reviewing that intent.

Brownfield: bulk invoice export

Finance wants one CSV for a small batch. An existing integration already calls the single-invoice function. Inspect its contract before changing anything. Starter: README · existing exporter and fixtures · baseline tests.

1 · Plan2 · Design3 · Build4 · Test5 · Deploy6 · Maintain
01 · Intent

Preserve what existing users depend on

  1. Run python -B -m unittest -v and record the two baseline results.
  2. Capture Finance's outcome and compatibility constraint in intent.md. Verify the filenames Claude cites.
Read README.md, invoice_export.py, and test_export.py without editing.
Draft intent.md for Finance's batch CSV request. Identify the caller-facing
behavior we cannot change and the questions we still need Finance to answer.
Reveal simulated result

The single export must retain its header, exact row shape, and KeyError for unknown IDs. Finance needs one ordered CSV for a small set of invoices; an unbounded export is out of scope.

Proceed when: The existing evidence and the new requirement are distinct. Next: Design

02 · Spec

Pick an additive change

  1. Compare overloading the public function with adding a separate, flagged entry point.
  2. Specify one header, input order, a default-off flag, and behavior for invalid batches.
Draft spec.md from intent.md. Compare two designs and favor preserving
export_invoice. Define acceptance cases for 1 to 10 unique known IDs, bad
batches, a disabled flag, and unchanged legacy output. Do not edit code.
Reveal simulated result

Choose new export_bulk() with a keyword flag. An invalid batch raises ValueError before rendering anything. The disabled path raises PermissionError; export_invoice() stays untouched.

Proceed when: You can explain how to turn the new behavior off. Next: Build

03 · Plan and diff

Work in a separate checkout

  1. Commit the approved intent and spec in your practice repo. Make a separate checkout with git worktree add -b lab-bulk ../invoice-bulk HEAD and open that checkout.
  2. Start Claude in Plan Mode, review the plan, and approve only the additive change. Review the diff, including the new files.
Plan the smallest bulk export change using the existing CSV renderer. Create
bulk_export.py and focused tests after I approve. Do not modify the legacy
exporter or its tests. Include a verification command and rollback check.
Reveal simulated result

Claude proposes two new files and no legacy changes. If the worktree lacks the spec, confirm it was committed in the source checkout before creating the worktree.

Proceed when: The legacy files match the baseline and the new entries are reviewable. Next: Test

04 · Evidence

Check compatibility and boundary cases

  1. Run python -B -m unittest -v. If a legacy test fails, inspect the change rather than adjusting the expected CSV.
  2. Check that an invalid batch never calls the renderer and flag-off leaves the legacy path available.
Read spec.md and compare it with the tests in a fresh context. Check one
header, reverse input order, exact batch limit, each invalid case, and the
legacy path with the flag off. Separate observed results from inferred ones.
Reveal simulated result and worked solution

Baseline: 2 tests. Worked solution: 6, including the unchanged baseline. Overlay bulk_export.py and test_bulk_export.py on a fresh starter copy and rerun.

Proceed when: The old and new contracts both have passing evidence. Next: Deploy

05 · Release

Rehearse a flag rollback

  1. Review and commit the candidate. Use a clean checkout of that revision as simulated staging.
  2. Run the smoke tests below. They check a successful enabled export, then the disabled path and continued single-invoice behavior. Save the output in the release record.
python -B -m unittest -v test_bulk_export.BulkExportTests.test_bulk_writes_one_header_and_keeps_request_order test_bulk_export.BulkExportTests.test_rollout_can_be_disabled_without_changing_legacy_export
git rev-parse --short HEAD
Reveal simulated result

Two smoke tests pass. If either fails, hold release and keep the feature off. A real feature flag needs its own permissions and audit trail; this local lab uses a function argument.

Proceed when: You know how to verify recovery, not just how to disable a flag. Next: Maintain

06 · Feedback

Turn a slow export into a scoped investigation

  1. Assume a practice threshold of 250 ms in two consecutive windows. Record the breach but do not infer a root cause from two samples.
  2. Rehearse flag-off again using the smoke test. Draft a follow-up intent to measure where time is spent.
SIMULATED 10:00 window_ms=312 threshold_ms=250
SIMULATED 10:05 window_ms=298 threshold_ms=250
Using these synthetic windows, draft incident.md with observations, unknowns,
flag-off verification, and a new intent for profiling. Do not claim the CSV
renderer caused the breach or make a code change during triage.
Reveal simulated result

Both windows breach the exercise threshold. Single export still passes after simulated rollback. Follow-up: measure data lookup and rendering separately under a fixed fixture and preserve the CSV contract.
