Knowledge and learning loop

Don't copy a transcript into project memory. Keep the decision and put the reusable lesson where it can change future behavior.

  1. Observe: The Brownfield agent kept rewriting the CSV header. Link the failing test and the accepted compatibility criterion.
  2. Diagnose: A new session could not tell the public CSV contract from an internal detail. Check whether the information was missing, ignored, or simply not tested.
  3. Choose a durable change: Keep exact behavior in a regression test. Add a short pointer in CLAUDE.md if it often matters; use a skill for a repeatable review procedure or a policy check for a mechanical requirement. Use an owned runbook for infrequent operational context.
  4. Review: Check the rule is scoped, version it with an owner, and exclude secrets, private logs, and incidental commands.
  5. Re-run: Repeat a representative change in fresh context. Did the agent preserve the header without a reminder? Does the test catch a deliberately changed expectation in a disposable copy? Remove stale guidance when it stops helping.

Keep the loops distinct: A production issue feeds a new product intent. A repeated mistake in the way the team or agent works improves a test, instruction, or control. One incident can teach both.

Closing thoughts: start with one play

Pick a change small enough to understand end to end. If review is the bottleneck, try a PR evidence checklist with a human reviewer. If bad assumptions are the bottleneck, try approved intent and spec before Build. Keep the existing approval path in both cases.

Compare a few similar changes before and after the pilot. Record queue time, rework, and escaped defects; don't infer a trend from a single change or use lines generated as a proxy for value. Keep the play if it makes the flow easier to verify without increasing risk. Then add the next play that solves a measured problem.

The goal is not to produce code faster at every step. It's to shorten the time from useful intent to a result you can explain, verify, release, and improve.

Glossary and Git primer

Artifact
A reviewable record, such as a spec, diff, test result, or incident note.
Acceptance criterion
An observable condition that must hold before you accept the change.
Branch, commit, and PR
A branch tracks a line of work, a commit records a snapshot, and a pull request asks others to review changes before merging them.
Greenfield / brownfield
Building something new / changing something that already has users, constraints, or contracts.
Smoke test and rollback
A short check of a release's key behavior, and a known path back to a safe state if that check fails.
Eval
A repeatable check of an agent's behavior on representative tasks, distinct from tests of the shipped application.

Use git status --short to see what changed, git diff to inspect tracked edits, and git diff --cached to inspect staged changes. Open newly created files directly or stage them before checking the staged diff.

FAQ

Do I need a Claude or Copilot subscription?

Neither is required for the browser exercises or hand-run Python labs. Agent-backed practice requires supported Claude Code access. GitHub Copilot is a separate product and is not required.

Is this the same as the AI-DLC framework on the parent site?

No. This course teaches Anthropic's six-stage playbook with Claude Code, Git, and simple artifacts. The parent site also teaches a separate framework with its own phases and tooling.

Do we need all six documents every time?

No. Keep the relevant decisions and evidence proportional to risk. A small bugfix may capture intent, verification, and rollback in the same PR.

Where should a team keep intent if it already uses a ticket tracker?

Choose one source of truth. If Git stores the accepted spec, link it from the ticket; if the tracker owns intent, link it from the spec and avoid two editable copies.

What if Claude requests credentials, network access, or a broad permission?

Decline anything the task does not require. Synthetic labs do not need credentials beyond signing in to Claude itself. Use a scoped tool or reproduce the action manually if your organization approves it.

What if the agent changes a test to make it pass?

Check whether the old assertion expressed the approved behavior. If so, preserve it and fix the implementation. If not, get agreement on the correction before changing it.

Can I use a real company repo for the lab?

Practice on the synthetic starter first. Apply the workflow to a company repo only after checking tool approval, data policies, repository trust, and release rules.
